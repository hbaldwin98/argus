### The seam (applies to every surface here)

Today every surface is a whole snapshot (`CheckoutsPage` = `Checkouts`, `CodePage`, `ExtensionsPage`, `ExtDialogPage`, `ViewsPage`, `SavedViewsPage`) sent by `Session` only when it differs from the last one (`connection/sent.rs` `Sent::take`). The page redraws the whole surface from each snapshot and carries a small amount of page-only state across the redraw. The port keeps the snapshots as the model; the page-only state listed in each surface becomes retained view state in GPUI. Nothing is predicted: a gesture is a `Call`, and the surface changes when the next snapshot says so (AGENTS.md, "the client never predicts"). Every rule below that says "sends" names the `Call` variant (`connection/page.rs`).

Key dispatch: a key outside a text field goes through the layer list `LAYERS` (`keymap.rs:853-886`); the layers of this group are `Extension` (a clicked extension view), `Files`, `Checkouts`, `Code` and `ExtensionPage`. In `LAYERS`, `Extension` comes before `Rail`; `Files`, `Checkouts`, `Code` and `ExtensionPage` follow `Features`, in that order. A text field (`Layer::Field`) and an extension dialog (`Layer::ExtensionDialog`) hold every key. A menu or dialog over the stage (`layerOpen`) holds the keys until it closes (`keymap.ts:114`).

## Surface CHECKOUTS: the Checkouts stage

Source: `ck/stage.ts`, `ck/says.ts`, `ck/table.rs`, `ck/stage.rs`, `session.rs:2438-2510`; `DESIGN` "Git and checkouts", "Navigation model".

What it is: the chosen repository's checkouts as a table (Checkout, State, Last commit, actions), the branches without a checkout folded under a row, a key bar under the table, and a side column about the selected row (or the Files panel in its place).

### gpui-kit mapping

- Table: `DataTable` (`table::{DataTable, TableState, TableDelegate}`), confirmed at https://gpui-kit.com/component/data-table.md: `TableDelegate` has `columns_count`, `rows_count`, `column`, `render_td(row_ix, col_ix, ...)` returning any `IntoElement` (so State cell dots, branch tags, and trailing buttons render in cells), `context_menu(row_ix, ...)`; `row_selectable(true)`; events `SelectRow(usize)`, `DoubleClickedRow(usize)`, `RightClickedRow(Option<usize>)`; row-mode keyboard: arrow keys, Home, End, PageUp/PageDown, Escape (unconfirmed for Escape: the page also lists Escape as "Clear selection" and ←/→ as column navigation, which clash with CHECKOUTS-32 and with selection always holding a row unless the table's keys are suppressed). Gaps seen on the page: no documented empty-state method (build the empty states outside the table); no documented way to insert a spanning "fold" row (the fold row is a section break: render it as a custom row element in the delegate or split into two tables / a header row above the branch rows); the `j`/`k` keys are not in the documented key set, so the port routes `j`/`k`/Enter/letters through Argus's own key layer (`Layer::Checkouts`) and keeps `selected` in Rust, setting the table's selection from the snapshot rather than the other way round.
- Row actions: `Button` (`.on_click`, `.tooltip`), the ⋯ menu is `PopupMenu` via `context_menu`/`dropdown_menu` (https://gpui-kit.com/component/menu.md): item kinds `menu`, `separator`, `label`, `PopupMenuItem::new(...).disabled(bool).on_click(...)`; shortcut hints appear automatically from action key bindings, which Argus's chord-routing does not use, so hints (`E`, `B`, `F`) need `PopupMenuItem` custom content. ### gpui-kit mapping

- File view: custom over `v_virtual_list` (https://gpui-kit.com/component/virtual-list.md: `Rc<Vec<Size<Pixels>>>` per-item sizes with variable heights, `VirtualListScrollHandle::scroll_to_item(index, ScrollStrategy::Top|Center)`, `offset()`, `set_offset(..)`, `scroll_to_bottom()`, rebuild the size vector when the data changes). Each line, each removal marker, each comment-box row and the end marker is one item. `Editor` (unconfirmed; https://gpui-kit.com/component/editor.md) is not a fit: that page documents no way to supply pre-highlighted spans (highlighting comes only from the Cargo-feature engine and the language name), no whole-line background API, no cursor event, and no `scroll_to_line`; Rust already sends highlighted runs `[text, kind]`. `Diff` (https://gpui-kit.com/component/diff.md) renders unified/split patches (`DiffFile::parse`, `DiffState`, `DiffLineRange`, `on_line_click`, `DiffAnnotation`) and owns its scrolling; the Code stage is a source file with a change wash, so it is "custom" here, though `Diff` with `DiffFile::unchanged` is the closest component to evaluate for the line selection model.
- Change ruler: custom (the Scrollbar page, https://gpui-kit.com/component/scroll.md and `scrollbar.md`, returned 404 when fetched; the catalog lists `scroll::Scrollbar`, and the virtual-list page shows `Scrollbar::both(&state, &handle)` with `.axis(..)`, but no mark or overlay support was confirmed). Paint the marks and band as a custom element reading the list's `offset()`.
- Files tree: flat rows on `v_virtual_list`, or `Tree` (https://gpui-kit.com/component/tree.md; same constraints as FILES: expansion must follow Rust's `open` flags, rows are `ListItem`s). The ignored fold row is custom.

- Search results grouped by file with fold: `Tree` with files as folders (`TreeItem::new(id, label).children(..).expanded(open)`) and hits as leaves, or custom rows; hit text with highlighted runs is custom rich text.
- Find and glob fields: `Input` + `InputState` (https://gpui-kit.com/component/input.md; `InputEvent::Change`, `PressEnter { secondary }`, `Focus`, `Blur`). ## Surface BLOCKS: the block renderer, containers and simple blocks

Source: `v/blocks.ts`, `v/ctx.ts`, `v/blocks/{board,callout,card,checklist,code,details,embed,fields,grid,list,log,row,stats,matrix,progress,timeline,tree}.ts`, `v/chip.ts`, `v/values.ts`, `v/refs.ts`, `argus-protocol/src/views/agent_view.rs` (the `Block` enum); scenes `agent-views`, `agent-view-page`, `saved-view`, `extension-stage`.

Every string in a block is an agent's, read from a ticket: it is drawn as text and nothing else, and colours come from the tone, never from the agent (`v/chip.ts:1-3`, `agent_view.rs:1-10`). Every block and every `Value` is drawn by one renderer for agent views, saved views and (tables, values) extension tables.

### Behaviours

1. CHECKOUTS-CODE-VIEWS-BLOCKS-1. A view's blocks are a vertical list. Each block has a path under its view (`<pane>/<id>.<index>` for an agent or extension view; a saved view's paths are -25); nested: a column adds `.<column>`, a tab `.<tab>`, a grid item `.<item>`, a row item `.<item>`, a table row's detail `.d<row>`). Page-only state (chosen tab, opened row, details open, tree fold, log scroll, drafts, filter, selection) is keyed by this path and survives a redraw of the view. Source: `v/blocks.ts:38-54`; `v/ctx.ts:44-51`.
2. CHECKOUTS-CODE-VIEWS-BLOCKS-2. A block whose path (after `<pane>/<id>.`) is in the view's changed set is drawn marked (flash once, or persistent while unseen; AGENTVIEWS-13). Source: `v/blocks.ts:46-54`.
3. CHECKOUTS-CODE-VIEWS-BLOCKS-3. `unknown` (a kind a newer Argus sent) draws a muted line "This needs a newer Argus to show."; an unknown value draws a muted `—` with the tooltip "needs a newer Argus". Source: `v/blocks.ts:127-129`; `v/values.ts:128-131`.
4. CHECKOUTS-CODE-VIEWS-BLOCKS-4. `section`: a label (the heading) with an open-saved mark when `opens` is set, then its blocks. `columns`: side by side (stacked when narrow). `divider`: a rule. Source: `v/blocks.ts:58-70,103-104`; `agent_view.rs` (Columns doc).
5. CHECKOUTS-CODE-VIEWS-BLOCKS-5. `tabs`: a tab bar (role tablist; each button role tab, `aria-selected`) and the chosen tab's blocks (role tabpanel). Clicking a tab selects it and redraws the body; the choice is remembered per block path, so a view that comes again keeps the tab being read; the remembered index is clamped to the last tab if tabs were removed. Source: `v/blocks.ts:133-165`.
6. CHECKOUTS-CODE-VIEWS-BLOCKS-6. `fields`: a label column beside a value column, each value drawn as a `Value`. Source: `v/blocks/fields.ts`.
7. CHECKOUTS-CODE-VIEWS-BLOCKS-7. `list`: no items draws "Nothing yet". An item with a `who` is a comment: person (avatar + name), age (`ago`, tooltip the raw `at`), chip, then the title and Markdown body; one without a `who` is an event: a dot and one muted line, its title placed before the meta. An `opens` mark follows the meta. Source: `v/blocks/list.ts:12-50`.
8. CHECKOUTS-CODE-VIEWS-BLOCKS-8. `stats`: tiles of label (with `opens` mark), the already-formatted value, an optional delta (coloured by the stat's tone, muted when neutral) and, when the trend has points, a spark of the trend in the tone. Source: `v/blocks/stats.ts:11-32`.
9. CHECKOUTS-CODE-VIEWS-BLOCKS-9. `code`: a header with the language and a Copy button, then the text in a monospace block (no highlighter). Copy sends `CopyText { text }` and the button reads "Copied" for 1.2 seconds, then its label again (repeat presses restart the timer). Source: `v/blocks/code.ts:7-19`; `system/copy.ts:8-21`.
10. CHECKOUTS-CODE-VIEWS-BLOCKS-10. `callout`: a note in the tone with a glyph (warn: triangle with mark; bad: circle with cross; good: circle with tick; info, and neutral and active, the info circle) and the text; role note. Source: `v/blocks/callout.ts:10-50`.
11. CHECKOUTS-CODE-VIEWS-BLOCKS-11. `card`: a bordered box; a non-neutral tone only tints the border; a head with the title (when given), the `opens` mark and the chip when either title or chip exists; the card's blocks; a foot with action buttons when it has actions. Source: `v/blocks/card.ts:14-39`.
12. CHECKOUTS-CODE-VIEWS-BLOCKS-12. `grid`: as many items per row as fit at a named minimum width (`sm`, `md` (default), `lg`; pixel widths are the page's), wrapping onto rows; each item is drawn as one block with its own index in its path. Source: `v/blocks/grid.ts:10-16`.
13. CHECKOUTS-CODE-VIEWS-BLOCKS-13. `details`: a summary line (text, `opens` mark, chip) that opens to its blocks. The agent's `open` is only how it starts: once the person toggles it the state is kept per path. Source: `v/blocks/details.ts:13-31`.
14. CHECKOUTS-CODE-VIEWS-BLOCKS-14. `row`: values and action buttons on one line, wrapping when narrow, aligned `start` (default), `spread` or `end`. Source: `v/blocks/row.ts:9-17`.
15. CHECKOUTS-CODE-VIEWS-BLOCKS-15. `embed`: draws another saved view's blocks in a bordered frame with its title, status chip, a stale chip, and an "Open" button (`OpenSavedView { id, from: <column> }`; title "Open this view in its own column"). A cycle (the view is already being drawn: any depth), a depth of 3 embeds or more, or a view the window does not hold draws a muted line `<view embeds itself | embedded too deep | view not found>: <id>` instead. The frame follows the view when it is saved again. Source: `v/blocks/embed.ts:16-48`; `v/saved/logic.ts:12-37`; tests `page/test/views/saved/logic.test.mjs` (18,23,30).
16. CHECKOUTS-CODE-VIEWS-BLOCKS-16. `progress`: label, an optional note beside it, and a meter filled to `value / max` clamped to 0..1 (a zero or negative max, an infinite value or an overshoot is never a broken bar), in the tone; accessible text is the note or the whole-number percent. The inline progress `Value` is a small meter with the percent. Source: `v/blocks/progress.ts:9-61`.
17. CHECKOUTS-CODE-VIEWS-BLOCKS-17. `timeline`: events in order, each with an age (`ago`, empty when no `at`), a dot in the tone, the title with an `opens` mark and an optional Markdown body. With lanes (any event names one): a grid of one column per lane (in first-seen order) with a lane header per column and one row per event, so row N of every lane is one step; an event with no lane goes in the first lane; the other lanes' cells in that row stay empty; narrow, the grid collapses to one column and each event carries its lane name. Source: `v/blocks/timeline.ts:12-58`.
18. CHECKOUTS-CODE-VIEWS-BLOCKS-18. `tree`: nested nodes; a node with children has a chevron button (`aria-expanded`, aria label the node's label) that folds and unfolds it; the fold state is remembered per node path (`<block path>/<i>/<j>`), the node's `open` is only the start; each node shows its label, an `opens` mark, its value (a `Value`) and chip, indented by depth. Source: `v/blocks/tree.ts:11-71`.
19. CHECKOUTS-CODE-VIEWS-BLOCKS-19. `matrix`: a table with column headers and row headers; each cell tinted in its tone with the tint strength = `round(clamp(weight, 0, 1) * 80 + 10)` percent (so the lightest is still a cell and the darkest keeps its text), showing the optional label; tooltip `<row> · <column>[: <label>]`; a missing cell is blank. Source: `v/blocks/matrix.ts:7-54`.
20. CHECKOUTS-CODE-VIEWS-BLOCKS-20. `checklist`: "<done> of <total> done" then items, each with a box (ticked when done), a hidden "Done: " / "Not done: " lead for screen readers, the label, an `opens` mark and a note. Read-only: the person does not tick. Source: `v/blocks/checklist.ts:12-37`.
21. CHECKOUTS-CODE-VIEWS-BLOCKS-21. `log`: a focusable scrolling box (role log) of lines: age (`ago`) when given, the level word (`debug`, `info`, `warn`, `error`), the text; each level its own colour. Scroll: a log the person has not scrolled up in follows the newest line; one scrolled up (more than 4px from the bottom) keeps its place across a redraw. The state is per block path. Source: `v/blocks/log.ts:11-37`; `agent_view.rs` (`LogLevel`).
22. CHECKOUTS-CODE-VIEWS-BLOCKS-22. `board`: columns of cards; a column header: title, a count of its cards, optional chip; a card: title, `opens` mark, chip, an optional value, an optional Markdown body. Source: `v/blocks/board.ts:12-51`.
23. CHECKOUTS-CODE-VIEWS-BLOCKS-23. An `opens` mark is a small "↗" button beside the element (title `Open <view title>`, aria `Open the saved view <title>`, dimmed with the title `No saved view <id> yet` when the view is not held) sending `OpenSavedView { id, from: <the column this is drawn in> }`; it does not bubble. A `view` value is a button reading its label, else the view's title, else the id, the same. Not offered where the element opens nothing. Source: `v/saved/link.ts:19-66`.
24. CHECKOUTS-CODE-VIEWS-BLOCKS-24. Tones: `neutral`, `good`, `warn`, `bad`, `active`, `info`. The agent picks the tone and the window owns the hue, so a view looks the same in every theme. A chip is a pill with the label in the tone; a dotted chip (dense tables) is a dot in the tone and the label in muted text. Source: `v/chip.ts:7-26`.
25. CHECKOUTS-CODE-VIEWS-BLOCKS-25. A saved view's blocks are keyed `saved/<panel>/<column>/<chain joined by '>'>.<index>`, not `<pane>/<id>`. Page-only memory (tabs, details, tree, log, table, form) is therefore per column and per embed, so the same view in two columns remembers separately. Saved views get no changed-block marking (`ctx.changed` is unset). Source: `page/src/views/saved/ctx.ts:20-33`; `page/src/views/blocks.ts:50`.
26. CHECKOUTS-CODE-VIEWS-BLOCKS-26. A dotted chip colours its word in the tone for `bad` only; for the other tones the word stays muted and only the dot carries the tone. Source: `page/src/views/chip.ts:182-183`.

CHECKOUTS-CODE-VIEWS-VALUES-4. `chip`, `chips`: pills in tone. `link`: a button reading the label that sends `OpenUrl { url }` (the URL is only a tooltip). `ticket`: the key (a link when it has a URL), the title muted, the status chip. `progress`: inline meter with percent. ## Surface TABLE: the agent's table block

Source: `v/blocks/table.ts`, `table/{bar,sort,details,memory,cell_text}.ts`; `agent_view.rs` (`Block::Table`); used by extension views with `RowPicks` (EXTVIEW-2 to -8).

1. CHECKOUTS-CODE-VIEWS-TABLE-1. No rows draws "No rows". Otherwise a table of the columns (numeric columns right-aligned in figures; optional columns dropped when narrow; the table scrolls sideways in a narrow panel). When `total` is greater than the rows sent, a line "Showing <rows> of <total> rows" follows. Source: `v/blocks/table.ts:66-72,262-266`.
2. CHECKOUTS-CODE-VIEWS-TABLE-2. Sorting is local and by header click: each header is a button; the first click on a column sorts ascending, a second click on the same column flips to descending (a click on another column starts ascending). The agent's `sorted_by` column is marked with the neutral state (`aria-sort` "other", arrow glyph shown) but its direction is not guessed; the first click then sorts ascending. Sort keys: numbers, bool and progress (`value / max`), duration and feature by magnitude; date and date_time by parsed time (unparseable dates last); text, person(s), chip(s), link, ticket (the key), code, path, commit (the sha), pane (label else id) and view (label else id) by lowercase text with locale comparison. Rows that compare equal keep their first-drawn order, so sorting twice does not shuffle ties. A copy writes the order the person sees. The sort state is not remembered across a redraw of the view (the table resets to the agent's order). Source: `v/blocks/table.ts:197-207`; `table/sort.ts:9-95`.
3. CHECKOUTS-CODE-VIEWS-TABLE-3. Filtering: more than 8 rows adds a search box ("Filter rows"); it matches case-insensitively against the lowercased text of a row's cells (joined by newlines); non-matching rows (and their opened detail rows) are hidden; a line "<shown> of <rows> rows" shows while filtering; the text is remembered per block path across redraws. Source: `table/bar.ts:15,82-110`; `table/memory.ts:27-34`.
4. CHECKOUTS-CODE-VIEWS-TABLE-4. Selection: only when the agent gives one key per row and `select` is `one` or `many`: a leading cell with a radio (group per block) or checkbox per row, with a select-all checkbox in the header for `many` that is checked when every shown row is selected and indeterminate when only some are; hidden (filtered) rows are neither ticked nor unticked by select-all. A "<n> selected" count shows; the agent's actions in the bar are disabled while nothing is selected. Selection is remembered per block path, trimmed to keys that still exist. Source: `v/blocks/table.ts:75-81,119-146,209-217`; `table/bar.ts:44-93`; `table/memory.ts`.
5. CHECKOUTS-CODE-VIEWS-TABLE-5. The bar: filter, counts, a spacer, the agent's table actions (a press carries the selected rows' keys in the order the person sees, `rows`), and "Copy as TSV". Copy sends `CopyText { text }`: a header line of titles then the shown rows' cell texts, tab-separated, newlines between rows, with any tab or newline inside a cell replaced by a space; the button reads "Copied" for 1.2 s. Source: `table/bar.ts:29-44,112-127`; `system/copy.ts`.
6. CHECKOUTS-CODE-VIEWS-TABLE-6. Row detail: when any row has detail blocks (`details`, one entry per row) a chevron column appears; the chevron (aria "Show row details", `aria-expanded`) opens the row to its blocks in a full-width row under it (blocks drawn with path `.d<row>`); a row with nothing to open has no chevron. Open rows are remembered per block path by row key (or `#<index>`), trimmed to keys that exist. Details are for agent tables only. Source: `table/details.ts:23-77`; `table/memory.ts`.
7. CHECKOUTS-CODE-VIEWS-TABLE-7. Long text cells (over 24 characters) truncate with the whole text as tooltip. Source: `v/blocks/table.ts:158-162`.

## Surface FORM: the form block

Source: `v/blocks/form.ts`; `v/actions.ts`; `argus-protocol/src/views/press.rs` (`ViewPress`, `Answer`, `relay`: limits, `MAX_ANSWER_BYTES = 4096`); no scene draws it.

1. CHECKOUTS-CODE-VIEWS-FORM-1. A form is fields the person fills in, then the submit action's button in a foot. Each field has a label and a control by input kind: `text` (one line, or four rows when `multiline`, placeholder, default), `number` (a number box with `min`, `max`, any step, default), `choice` (a select of the options, default else the first), `toggle` (a checkbox shown before its label on one line, default), `date` (a date box, `YYYY-MM-DD`, default). Multi-line text and fields with long labels span both columns. Enter in a field does not submit (the form's native submit is prevented). Source: `v/blocks/form.ts:18-49,62-135`.
2. CHECKOUTS-CODE-VIEWS-FORM-2. The text typed is kept across redraws of the view, by form path and field name (text, a number's text, a choice, a date as typed; a toggle as its state), so the defaults are not put back under the person's fingers; a stored choice that is no longer among the options is ignored. The drafts of a form are dropped when it is submitted. Source: `v/blocks/form.ts:16,62-135,36-39`.
3. CHECKOUTS-CODE-VIEWS-FORM-3. Submit builds the answers at the press: text, choice and date answer `{ name, value: { kind: "text", value } }`; number answers `{ kind: "number", value }` and is left out when the box is empty or not finite; toggle answers `{ kind: "bool", value }`. It sends `PressView { pane, press: { view, action: <submit.id>, rows: [], form: <form id>, answers } }` (or `PressSavedView`), through the action button's usual rules (confirm question first when the submit has one; pending and disabled until the view is shown again; disabled when the daemon cannot take presses). Source: `v/blocks/form.ts:36-49`; `v/actions.ts:31-96`.
4. CHECKOUTS-CODE-VIEWS-FORM-4. What reaches the agent is only what the view could have produced (the daemon reads the press against the view and cuts an answer past 4096 bytes). Source: `argus-protocol/src/views/press.rs:1-24`.
